# 08 部署运维与风险应对

## 1. 环境规划

| 环境 | 数据与端口 | 模型 | 权限/用途 |
|---|---|---|---|
| unit | 临时目录/内存ASGI，不监听生产端口 | fake | 无公网、无生产配置 |
| integration | 独立SQLite和文件，后端18000、前端15173 | fake或独立测试端点 | 业务隔离，不复用生产任务ID |
| benchmark | 独立目录，模型18082、后端18002 | 已批准的同一GGUF只读 | 与生产推理互斥，防止64GB内存双重驻留 |
| production | 保留现有data目录，模型18080、后端8000 | 已认证CPU配置 | 非管理员；默认loopback；维护窗口发布 |

Vite 5173是开发服务，不作为生产部署。生产构建 web/dist 由现有后端静态资源机制提供。若需内网访问，由企业批准的 TLS 反向代理终止 HTTPS；不得直接将未鉴权的模型 `/slots`、`/metrics`、管理API暴露公网。

主认证平台 Windows 11 x64 / Python 3.12 / P0锁定Node版本；Ubuntu 22.04 x64为第二认证矩阵，用同一Python服务和独立OCR运行时。Windows 10/其他Python版本若未跑测试，报告“不在本次认证范围”，不能沿用旧README一概承诺。

## 2. 原生离线准备

按以下先后顺序：

1. 盘点当前服务、用户工作树和本地文件，确认维护窗口；不拉取覆盖未提交改动。
2. 在受信任联网构建机解析并锁定Python全部依赖，生成带hash的lock、目标平台wheelhouse及许可证清单；OCR大依赖与基础安装分组，但不得未经兼容测试删除既有依赖。
3. 固定npm lock和Node/npm版本，预填充npm cache；原生包按Windows/Linux分别准备。离线安装不能假设仅有package-lock就够。
4. 校验GGUF、llama-server及其DLL/so、tokenizer/template、Embedding/OCR资源hash。使用预编译认证包时CMake不是运行必需；只有自行编译才需要构建工具。
5. 离线机器原生创建venv，使用 `pip install --no-index --find-links <wheelhouse> --require-hashes -r <lock>`；然后 `pip check`。禁止临时连公网补包。
6. 前端 `npm ci --offline --cache <bundle-cache>`，失败明确缺包，不自动回退联网；构建资产可由CI打包后直接部署。
7. 设置APP_CONFIG绝对路径，所有新增目录位于授权数据盘；TEMP/TMP指向可写验证/运行目录。不得仅为了本次验证清理用户C盘数据。
8. 初始化测试新库、执行迁移和预检；生产库必须先备份，详见05。

配置中app/data/model路径、端口、并发、日志、OCR和策略分别校验；启动脚本必须打印最终路径/版本/CPU线程（不打印密钥），确保PowerShell与Python启动方式行为一致。

## 3. 新运维工具契约（T60待实现）

`bin/audit_ops.py` 子命令：

| 子命令 | 输入 | 动作与退出语义 |
|---|---|---|
| preflight | `--config` | 检查schema、目录权限、存储、模型/tokenizer/端口、OCR；0可运行，2缺资产/错误配置，3运行状态冲突 |
| status | `--config --json` | 只读服务、队列、在途请求、版本和容量；不显示合同正文 |
| drain | `--config --timeout-seconds 900` | 停接单并等待在途任务；超时非0，不自动kill |
| resume | `--config` | 模型slot状态可确认且无冲突时恢复接单 |
| backup | `--config --output-dir` | SQLite一致性备份、业务文件清单及hash；失败非0 |
| cleanup-plan | `--config --output` | 只生成到期诊断/缓存清单，不删除 |
| cleanup-apply | `--plan --approved-by` | 校验计划hash/路径/在用状态，只删获批清单；全程审计 |

迁移工具 `bin/migrate_audit_jobs.py --config <path> --check|--apply`；`--check`只读，`--apply`验证备份/版本并事务迁移。CLI必须有 `--help`，脚本任何阶段失败返回非0，不以“日志打印错误但exit0”掩盖失败。

## 4. CI/CD 顺序

仓库现有 `.github/workflows/ocr-ci.yml` 保留；新增合同审计工作流可在企业自建Runner执行，不依赖GitHub公网。流水线同时提供本地Python/PowerShell入口，权限受限环境可手动执行同一步骤。

1. Checkout指定提交并记录patch摘要；预检扫描密钥/大模型/保密合同，禁止打进源码包。
2. 使用锁定离线依赖安装；输出SBOM、Python/npm依赖安全扫描。漏洞数据库版本和更新时间入账，离线库过旧标记未完整验证。
3. 静态检查、后端编译/单元/集成、前端lint/单测/build、迁移新库/旧库副本测试。
4. 受控真实模型性能与质量作业在专用Runner串行运行；耗时长可设人工门，不得以未运行当通过。
5. 打包带commit、config schema、DB schema、model/runtime hash的release manifest；产物签名或企业校验流程。
6. 业务/运维批准后进入维护窗口，备份、drain、确认进程退出、迁移、启动、冒烟、恢复接单。
7. 发布后至少完成3份合成合同和1份获授权样本观察，记录24小时失败率/资源变化，再关闭发布观察期。

任何stage非0必须停止后续发布；允许开发者收集更多诊断，但不得继续生产部署。Git commit/push/PR按用户授权执行，CI配置生成不等于授权推送。

## 5. 启停与回滚流程

1. 使用现有 `bin/start-services.ps1` / `bin/start-services.py` 为基础，T60补充生产模式、固定端口、预检及线程参数；现有默认“端口自动切换”生产设 `APP_PORT_AUTO_SWITCH=0`，占用即失败。
2. 运行目录增加OS文件锁；核实PID和命令行匹配项目再停止，不按所有python/node/llama进程批量kill。
3. 停机时先drain，队列剩余请求用户可见；超过900秒维护窗口不足则取消发布，不自动终止合法长任务。
4. 快照、迁移、启动后一份合成合同检查进度、引用、定位、结果落库和导出。无法建立模型tokenizer能力则不开放v2接单。
5. 回滚恢复上一认证保护版本及配置；数据库采用05策略，新增表不自动删。回滚后重新做同样冒烟并登记任务中断影响。
6. 生产恢复数据备份需明确RPO和发布后新增数据保护方案；建议目标RPO≤24小时、RTO≤60分钟，必须在演练中实测，未测不可承诺。

## 6. 监控指标与告警

元数据日志字段统一 `ts/level/event/request_id/job_id/chunk_id/attempt_id/owner_hash/model_hash/elapsed_ms/error_code`。owner_hash只在日志使用，不取代DB权限。命令日志、截图索引保留时区。

| 规则ID | 指标/阈值 | 级别与动作 |
|---|---|---|
| AL01 | 在途job心跳>15秒 | warning；>30秒critical，检查执行器；不自动重跑 |
| AL02 | 模型请求>480秒 | warning；600秒截止，失败策略见03 |
| AL03 | running总时长>2700秒 | warning；5400秒截止 |
| AL04 | 队列3个持续>60秒 | warning；拒绝新增429，不扩并发 |
| AL05 | 进度API P95>500ms 连续3个1分钟窗口 | warning；>1秒critical，排查事件循环/DB锁 |
| AL06 | 任一done任务coverage<1或预算违规 | critical；立即停止接单，禁止发布结果 |
| AL07 | 数据盘剩余<10GiB或<15% | warning；<5GiB或<5%停止新上传并返回507 |
| AL08 | 系统盘剩余<5GiB | warning；<2GiB停止接新单，提示人工清理 |
| AL09 | 主机内存>90%持续60秒 | warning；>95%停止接单，不自动杀其他进程 |
| AL10 | 最近10个终态任务失败≥2 | warning；首例OOM/持久化失败直接critical |
| AL11 | 单日志>10MiB未轮转或诊断目录>1GiB | warning；按批准策略清理诊断，不删业务源文件 |
| AL12 | slot状态无法确认且请求已中断 | critical；执行器暂停，人工核实slot释放 |

任务进度API提供业务状态，`/health`保留现有语义；新增受鉴权运维摘要端点或CLI输出深度健康，不能拿 `/health=ok` 代表模型空闲。

结构化metadata每天/10MiB轮转，最多7份/模块；性能计数汇总输出JSON便于接入企业监控，无需本期安装监控平台。开启原始trace必须有诊断工单，关闭后按保留期清理。

## 7. 风险清单与应对

| 风险 | 触发/影响 | 预防/回退 | 责任与验收 |
|---|---|---|---|
| 修漏段后更慢 | 全文实际送审量增加 | 先建立B1，再去重/缓存；不恢复截断 | 算法负责人，G1/G5 |
| 预算估算不准 | tokenizer与模板不同 | 固定hash并校准；超限重规划一次 | 模型负责人，UT08 |
| 缓存无效 | 版本不支持或前缀变动 | A/A/B探测；默认关闭，性能不造数 | 模型负责人，PT01 |
| 输出截断 | 风险密度高 | 自适应缩小主块/有界重试；保持严格JSON | 算法负责人，UT09 |
| 取消不停止服务端 | HTTP断连但slot仍忙 | 暂停调度，确认释放；不盲目启动下一单 | 运行时负责人，IT05 |
| SQLite锁/磁盘满 | 心跳/结果无法写 | 短事务、容量预检、真实失败 | 后端负责人，IT03/OP02 |
| 法规与模型更新 | 旧缓存/证据不适用 | 冻结snapshot/hash，更新失效 | 质量负责人，QT01 |
| 权限泄漏 | task ID可猜/跨用户共享 | owner过滤、受限日志、缓存隔离 | 安全负责人，IT08 |
| 原生依赖崩溃 | Windows OCR/ONNX/torch不兼容 | 认证版本、隔离进程回归；禁用未经认证可选OCR | 运维负责人，OP01 |
| 法律误报/漏报 | 压缩或小模型降低质量 | 专家金标、人工复核、不自动裁决 | 业务负责人，QT01 |
| 旧代码回滚漏审 | 恢复到不安全v1 | 只允许含coverage保护的版本 | 发布负责人，OP04 |

## 8. 小模型/核显实验的进入条件

仅在G5有完整数据、业务批准新增实验后进行。记录许可证、离线来源、SHA256、峰值内存和质量差异；实验模型不得偷偷复用“small_model=auto”同一实例。核显共享内存，吞吐收益必须实测，不能以“存在GPU”推导能加速。未经审批不修改主板内存频率或BIOS。
