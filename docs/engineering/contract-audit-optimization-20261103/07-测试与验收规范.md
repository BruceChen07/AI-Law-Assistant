# 07 测试与验收规范

## 1. 隔离与证据先行

1. 所有测试必须使用独立 APP_CONFIG/数据库/文件/trace/memory/TEMP。不得直接 import `app.main` 后再替换配置，因为 import 可能初始化真实模型/库/管理员。
2. T01先补 `create_app` 测试注入及禁用真实 bootstrap 的 fixture，保持生产默认行为不变。随后改造现有会触碰生产配置的测试。fake LLM 测试与真实模型基准彻底分目录和日志。
3. 测试身份由 fixture 注入或隔离库创建；禁止重置生产管理员密码。
4. 前后保存真实配置、业务数据库、源文件的摘要/mtime，证明测试未写生产；在线库不能只用主db文件hash判断内容，使用只读快照核查。
5. 每次测试记录 start/end（带时区）、命令、cwd、exit_code、配置hash、git HEAD/dirty摘要、runtime/model hash、输出日志路径、测试统计。
6. 原生访问冲突、磁盘满等计为环境/运行阻断，不把此前部分 passed 当作完整通过。隔离复跑要保留原失败结果。

## 2. 数据集

`tests/fixtures/audit_v2/manifest.json` 逐样本记录 sample_id/source_hash/type/language/pages/expected_source_spans/expected_risks/authorization_ref。合成数据可入库；真实合同只在受限外部fixtures目录，manifest使用不泄密ID。

最小覆盖：

- 文本PDF、扫描PDF、文本/扫描混合页、DOCX、中文、英文、双语、无正文、乱码、加密/损坏文件。
- 1页/28页/长合同；797碎片回归；单条款超过上下文；结尾有关键税务条款；跨页条款。
- 表格税率、否定/例外、合同内prompt注入、相同文件名不同内容、同文件不同用户。
- 跨条款已有约定但前文未出现；缺少白名单证据；相同风险多轮重复；重试后风险冲突。
- 限额50 MiB边界、zip bomb、中文文件名、长路径、磁盘不足和只读目录。

专家样本至少20份，至少5份含高风险，至少5份含跨条款误报反例。若少于20份可做开发回归，但正式质量验收标记 BLOCKED。源样本SHA256固定，修改后必须重建基线。

## 4. 性能实验协议

### 4.1 三种基线不得混淆

- B0：历史11次调用36分51秒，仅用于诊断；没有完整结果，不参与“整单提速百分比”计算。
- B1：P1完成全文覆盖保护后，相同主模型和原有硬件参数下的**完整正确运行**。
- B2：P2～P5最终候选，同B1输入与质量门槛。

性能公式 `speedup = 1 - median(T_B2) / median(T_B1)`。T从任务running开始到报告事务commit；分别记录queue wait和上传耗时，不计入该公式。运行失败不从报表删除，而是记录失败率；存在覆盖不完整的运行不参与合格性能样本。

### 4.2 测量步骤

1. 先用3份代表样本筛参数，每候选一次冷启动、两次暖运行；不超过当前硬件内存。
2. 从合格候选选2组，用20份专家样本，每份每组3次暖运行，交替B1/B2顺序减小温度/后台负载偏差。每类再选一份做3次冷启动。
3. 暖运行=模型已加载，但任务/用户KV cache按生产策略清空；任务内前缀复用允许。冷启动包含单列model_load_ms，不把载入时间混到稳态推理。
4. 禁止后台并行跑全量测试、下载或其他LLM。记录内存、进程CPU、磁盘可用、系统负载、模型hash、启动命令和电源方案；不擅自修改BIOS/电源全局配置。
5. 记录按块input/output/cached tokens、TTFT/prefill/decode（不可测为null）、调用总耗时、重试数、coverage、风险数及人工质量结果。
6. 报告配对中位数、P95、每样本分布，不用一次最快值。多次样本统计不等于多个独立合同样本，必须列 sample_count 与 run_count。

R06提速目标≥30%，28页≤25分钟是目标而非保证；专家质量不下降优先。若缓存优化无收益，需要列出命中率与token顺序原因，不能宣称已经加速。

基准CLI（M12待实现）契约：

```text
python bin/benchmark_contract_audit.py
  --config <隔离配置绝对路径>
  --samples <manifest.json绝对路径>
  --output-dir <新的证据目录>
  --profile B1|B2
  --warm-runs 3
  --cold-runs 1
  [--manage-model]
```

样本manifest格式为 `{schema_version:1,samples:[{sample_id,path,sha256,type,language,gold_path,authorization_ref}]}`；只接受样本根目录内的文件。每份样本的线程/batch配置来自本次config，不在一轮中途修改；参数搜索由多个独立config和output-dir完成。

默认不管理模型生命周期；若请求cold-runs>0却没有 `--manage-model`，返回配置错误并要求操作者提供冷启动确认，不能把暖运行算冷启动。`--manage-model` 只允许管理脚本自己在benchmark端口启动的进程，必须与生产PID/端口不同；不允许杀生产模型。默认warm-runs=3、cold-runs=0，正式协议由操作者显式传参。

输出 `runs.jsonl` 每行包含 `{run_id,sample_id,profile,repeat_index,cold_start,git_head,config_hash,source_hash,model_hash,runtime_hash,template_hash,started_at,finished_at,status,queue_wait_ms,model_load_ms,total_elapsed_ms,input_tokens,cached_tokens,output_tokens,retries,coverage,quality_ref,peak_memory_bytes,error_code}`；失败也必须有行。另输出 `summary.json` 和 `report.md`，列样本数/成功失败阻断数、P50/P95及配对收益。退出码0表示全部计划运行成功，1表示测试失败，2表示输入/能力前置缺失；性能/质量阈值不达标仍返回1。

### 4.3 质量判定

标注风险至少包含 clause/source range、risk_category、有效法规依据、severity。预测匹配需同时满足来源/风险语义/法规依据，由两名审核者裁决争议；不能仅比较字符串或交给同一模型自评。

`recall=匹配金标风险数/金标风险数`；`precision=匹配预测数/全部正式预测数`；重复预测只匹配一次。needs_review 不算已确认正确预测，另列人工复核负担；不得通过全标needs_review获得虚假高精确率。高风险召回100%的验收要求金标高风险都被正式verified结果匹配；仅出现在needs_review中不算该门通过，另报“已提示但未确认”比例。任何高风险不得静默丢失在无说明的rejected中。

## 5. 命令与执行条件

下列 prepare 脚本为T01待实现契约：`--output-dir <绝对路径> --mode unit|integration|benchmark`，创建隔离config与目录，拒绝输出到生产data_dir，打印使用命令，退出0/非0。必须先实现脚本，再运行以下顺序，不得直接复制“尚不存在”的命令假报成功。

```powershell
# 仓库根目录执行；prepare脚本完成后使用。
& ".\app\.venv\Scripts\python.exe" bin/prepare_audit_validation.py --output-dir "D:\AuditValidation\run-001" --mode unit
$env:APP_CONFIG = "D:\AuditValidation\run-001\config.json"
$env:TEMP = "D:\AuditValidation\run-001\tmp"
$env:TMP = $env:TEMP
& ".\app\.venv\Scripts\python.exe" -m pytest tests -ra --tb=short --junitxml="D:\AuditValidation\run-001\pytest.xml"
```

前端在 `web` 工作目录依次执行 `npm ci`（离线环境见08）、`npm run lint`、`npm run test -- --reporter=default --reporter=junit --outputFile=<绝对JUnit路径>`、`npm run build`。每条保存退出码；前一步失败不意味着可以省略报告。基准脚本独立使用 benchmark 配置，不与unit测试共享目录。

真实浏览器验证必须在隔离前后端端口执行，截取含阶段、百分比、任务ID的页面；截图包含敏感内容先脱敏。未运行浏览器不能把Vitest当作浏览器已验证。

## 6. 报告与验收签署

每次输出：JUnit、原始stdout/stderr、performance.json、quality.csv、问题表、截图索引。每个问题含 ID/分类/严重性/版本/时间/前提/复现步骤/实际与预期/证据/影响/规避/负责人/状态。

零发现也要记录测试边界。跳过、失败、阻断、通过数量分别统计；最终验收人分别签署功能、质量、安全、运维和性能。没有专家质量签字只能交付“工程验证通过，法律质量未验收”。
